## Verdict

**The batch on `dev` cannot yet produce a valid measured run, and five of the reasons were not known.**
One is a wrong name that stops every reset. The other four make a run's record say something that did not
happen: the wrong Incident, the wrong arm, only the successes, and no injection time.

## New findings

### V1 (Blocker): the runner names an Application that does not exist

- **Evidence:** `runner.py:46` `APPS = ("sample-api-dev", "dependency-db-dev")`. VERIFIED live
  (`kubectl -n argocd get applications`): the Application is `dependency-db`, and it tracks `main`.
- **Effect:** `plan_refresh` annotates `dependency-db-dev`, the step fails, and `execute` raises: every
  `reset` and `refresh` stops there. `wait_synced` can never return True, so a run would end
  `applications_not_synced` after 600 s.
- **Fix:** one line, plus a test that reads the names from `platform/argocd/applications/`.

### V2 (Blocker): the run's Incident is whichever ends first

- **Evidence:** `batch.py:580-598`: any Incident whose uid is new, in any namespace, for any alert, ends the
  run when it reaches a terminal phase; `ended[0]` gives the run its terminal phase.
- **Scenario 1:** a spontaneous nexus-prod Incident (four on 2026-11-07, between 07:20Z and 11:50Z) ends
  `Recommended` during a nexus-dev run. The run is recorded valid with terminal `Recommended`.
- **Scenario 2:** in S2 the Traffic alert fires before the Cpu alert. Its Incident ends
  `Dismissed / no_action_required` (R1 rule 5), the run ends, and the scale is never observed.
- **Wanted:** the Incident of the injected namespace, detected after the injection; every other Incident
  recorded beside it.

### V3 (Blocker): only successful S1 remediations would count

- **Evidence:** `batch.py:520-532` holds every scenario but S2/S4/S6 to the baseline request rate at the
  end of the run; `precheck.py:360-370` reads the rate in each namespace, within ±10 %.
- **Scenario:** S1 where NEXUS does not restart (R3 escalates, the gate blocks, or verification fails).
  The pods stay hung, the rate in nexus-dev stays near 0, and the run is voided `locust_end_check` and
  requeued. Runs where the restart worked pass. Remediation success for S1 would be 100 % by construction.
- **Wanted:** the end check tells "Locust stopped" from "the service does not answer": read Locust's own
  state and user count, not the server-side rate, when the Incident did not end `Resolved`.

### V4 (Blocker): the arm is a label, not a setting

- **Evidence:** `runner.py:239-260` writes `advisoryChecks` and `breakerEpoch` only. The operator reads
  `reasonerEndpoint`, `reasonerMode` and `reasonerModel` from the same ConfigMap (`config.py:44-49`), and
  nothing in the harness sets them per cell. `batch.py:592-598` reads `fallbackUsed` and never compares
  `status.reasoner.mode` or `modelId` with the cell.
- **Scenario:** C1 (R1) and C2 (R3) cells alternate in one queue. All of them run under whatever the
  operator was last configured with, and every metric is grouped by the cell's `reasoner`
  (`batch.py:285`, `metrics.py:123`).
- **Wanted:** the reset writes the cell's arm; the run is not valid unless the Incident's
  `status.reasoner` matches it (a fallback aside).

### V5 (Blocker): no injection time

- **Evidence:** `batch.py:574-576` discards the step log; the run record has `started_at` (before the reset
  and up to 20 minutes of pre-checks) and `ended_at` only. `export-results.py` needs `--injection TS` by
  hand; `metrics.py:191`, `196` compute detection latency and MTTR from it.
- **Effect:** in an unattended batch of about 216 runs nothing holds the start point of two §21 metrics.
- **Wanted:** the batch stamps the injection on the run record (for S3, when Argo CD applied the revision).
