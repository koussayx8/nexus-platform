# M3 boundary red-team review — 2026-11-15

Claim under test: "nothing the operator or a bad reasoner does can leave the
4-action envelope".

**Result.** No path was found by which the `nexus-operator` ServiceAccount, or a
proposal, causes a cluster mutation other than a scale within [1, 5] or a pod
eviction, in `nexus-dev` or `nexus-prod`. The claim holds in that form. It is
weaker than it reads in four ways: the envelope is per namespace, not per target
(F2); an approval is a 15-minute licence, not a single use (F5, F6); at L2 the
compensation appears to be refused by K3 (F7); and the containment matrix does not
test any of these (section 4). `nexus-dev` is at level 3 live and in Git, so K3 is
not on the path today (F1).

**Scope and method.** Review only. Tree: `origin/dev` at `2ae7030`. Cluster:
read-only `kubectl get` and `auth can-i --list`, context `default`, 2026-11-15.
No cluster write, no server-side dry-run, no fix. Policies were read in full
(K1–K6); the operator code only around compensation (`act.py:974-1040`).

Labels: **VERIFIED** = output of a command run in this session. **UNVERIFIED** =
derived from reading policy or code, not exercised; the settling test is named.
Findings are numbered F1–F14.

## 3. L2 approval path

F1 (VERIFIED): `nexus-dev` carries `nexus.io/autonomy-level=3` live, and
`overlays/dev/namespace.yaml:9` sets `"3"`. K3 skips level 3. The brief says "L2
approval at nexus-dev"; that is not the current state. Nothing below is exercised
live today.

| Topic | Finding | Status |
|---|---|---|
| Time of check vs time of use | No gap at the authoritative layer: K1, K3 and K4 read the namespace, the Incidents and the Kill Switch at admission of every request, dry-run and real | VERIFIED (policy text) |
| F5: the approval pins the destination, not the starting point | K3 pins namespace, name, action and `replicas`. Approved "scale to 3" while at 2; if the count is 5 at execution, 5 → 3 is admitted — a scale *down* under an approval read as a scale up | UNVERIFIED live |
| Level change mid-flight | 2 → 3 removes the approval requirement at once for pending Incidents; 3 → 2 refuses the remaining evictions of a restart in progress and its compensation. Only an admin changes the label | VERIFIED (policy text) |
| Kill Switch mid-flight | Remaining evictions and compensation refused (K4); the workload stays partly restarted or at the changed count. Designed (§16A); matrix covers compensation only | VERIFIED (policy text, `act.py:1006-1013`) |
| F7: compensation at L2 | Compensation scales to `plan["previous"]` (`act.py:1015-1017`). K3 admits a scale only when `approval.parameters.replicas` equals the requested count, which is the approved value, not the previous one. So at L2 the compensation is refused and the Incident ends `Escalated / compensation_blocked` with the changed count in place. No K3 test or ADR text covers it | UNVERIFIED live — one `kyverno test` case |
| F8: forged `status.proposal` | K5 binds the approval to `status.proposal.{hash, actionId, parameters.replicas}`, all written by the operator and never recomputed outside it. A compromised operator cannot widen what K3 admits: target is immutable `spec` (C1, C3), and action and replicas are written by the approver. It *can* show any diagnosis and evidence beside them, and rewrite the record after approval. The human approval is as good as what the client displays | VERIFIED (policy and CRD text) |
| F6: replay | K3 has no notion of use. Until `expiresAt` (at most 15 min) an approved Incident admits: the same scale again; any number of evictions of `<target>-*` pods; and requests made for a *different* Incident on the same target. K3 does not read the Incident's phase, and could not trust it (F4) | VERIFIED (policy text) |
| Operator-made Incidents | K6 lets the operator create `detector` Incidents for any C3 target, so a compromised operator can manufacture requests for approval. `spec.approval` from the operator is refused by K5 and by RBAC (no update) | VERIFIED (policy text, RBAC) |

## 5. Notes for ADR-040 (Telegram bot) and ADR-041 (C8)

Design notes only, from `TASKS.md` D9, D15 and `nexusctl/README.md:33-36`; no bot
or C8 code exists on `dev`. All UNVERIFIED.

**Telegram bot — impersonation of `koussay-approver`.**

| Risk | Note for the ADR |
|---|---|
| The bot's credential *is* the approver | Whoever holds a credential that can impersonate `koussay-approver` in group `nexus-approvers` can approve. It must not live in the operator pod or namespace, or F8 becomes "a compromised operator approves itself" and L2 collapses into L3 |
| Scope of impersonation | A Role limited to `impersonate` on user `koussay-approver` and group `nexus-approvers` by `resourceNames`, nothing else. K5 then stamps `approvedBy: koussay-approver`; the audit log shows the bot as the impersonator — say which one the thesis reports |
| Who pressed the button | Allow-list the numeric Telegram user ID and the private chat ID; refuse group chats. Long polling, or a webhook with `secret_token`; an open webhook lets anyone post a forged callback |
| What you see is what you approve | The button's callback carries the Incident name and the proposal hash *shown*; the bot patches with that hash and never re-reads at click. Target, action and replicas on screen come from the Incident fields K5 binds, not from Reasoner text |
| Explain and Note | Explain is Reasoner-written text aimed at the approver; Note is free text into an untrusted Reasoner. Neither may change what the Approve button sends |
| Replay | C2 (write-once) refuses a second decision; a stale button must fail on the hash |
| Bot token theft | Lets an attacker read alerts and message the owner as the bot; it does not forge the owner's `from.id`. Rotate through BotFather; token in `~/.nexus/keys.env`, never in Git |

**C8 — machine-account fork token.**

| Risk | Note for the ADR |
|---|---|
| Token reach | No write to `koussayx8/nexus-platform`; push only to the fork. A fine-grained token may not be able to open a pull request against a repository it has no access to — D15's 10-minute test settles it |
| Where the token lives | If it is mounted in the operator, a compromised operator can open arbitrary pull requests. Still no merge, but it is a channel outside the four-action envelope and should be stated as such |
| Content of the pull request | The diff must be a mechanical revert computed by trusted code, never Reasoner output. Title and body carry Reasoner text: treat as untrusted (mentions, links, text shaped like an approval line — rule 11 already ignores it) |
| CI on fork pull requests | VERIFIED: no workflow uses `pull_request_target` or `workflow_run`; all use `pull_request`, so fork runs get no secrets. Keep it so, and require approval for fork workflow runs |
| Merge | No auto-merge; the owner merges under rule 11. A merge into `experiment/dev-state` is a cluster change through ArgoCD, so the review of that diff is the control |
